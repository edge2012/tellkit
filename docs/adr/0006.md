# 0006 — Containerized dependencies

**Context.** Rendering depends on fonts, Python libraries and an external encoder working together. An LGPL FFmpeg variant without libx264 previously failed with Unknown encoder, leaving an entire batch without movies. Installing a binary named FFmpeg was therefore insufficient to establish that a machine could complete the rendering pipeline.

**Alternatives.** One route installs dependencies independently on each machine and diagnoses incompatibilities after jobs fail. The other distributes a common container image with the required libraries, fonts and encoder capabilities. Independent installation is flexible, while the image makes dependency selection a shared, inspectable part of the release.

**Decision.** Choose a common image with pinned Python packages and a GPL-enabled FFmpeg build that includes libx264. Validate encoder availability before starting expensive frame work. The failed batch supplies the reason for checking capabilities rather than relying on the executable name or assuming every distribution enables the same codecs.

**Consequences.** Images require rebuilding for dependency and security updates, and the base image still affects reproducibility. Font licenses must travel with the assets inside the image. Container packaging also leaves resource management to the runtime: a correct dependency set cannot prevent memory exhaustion or clean up orphaned children without lifecycle controls.
