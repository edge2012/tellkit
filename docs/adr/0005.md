# 0005 — Go control and Python media

**Context.** Request orchestration and frame drawing have different resource profiles. On the same batch of content, single-episode rendering improved from 555 seconds to 46 seconds, with individual frame drawing at 2.3–3.8 milliseconds. Rendering performance is substantial enough to deserve its own execution and measurement boundary.

**Alternatives.** One route puts request handling and media work into a single runtime. The other keeps orchestration in Go and media work in Python, connected through explicit contracts. A single runtime reduces interface work; the split preserves the image-processing ecosystem while allowing request orchestration to evolve separately.

**Decision.** Choose Go for control and Python for media. Treat storyboard data, job state, artifact identity and failures as contract fields rather than implicit process knowledge. The measured render improvement reinforces the value of examining media work directly: total request duration alone cannot identify which rendering stage deserves attention.

**Consequences.** Two runtimes require coordinated schema changes and consistent error interpretation. Process failure must cross the boundary as a useful job outcome, and cancellation must reach media subprocesses. The split also creates packaging work; it does not by itself ensure that a timed-out request stops the expensive computation it started.
