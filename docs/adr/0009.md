# 0009 — Memory failures

**Context.** Failed rendering subprocesses survived as orphans, retaining 1.2–1.4 GB each. Two episodes exhausted a 4 GB machine. The visible symptoms were intermittent 503, LEASE_LOST and ENCODE_FAILED outcomes, which appeared to implicate different components even though they shared the same underlying pressure on memory.

**Alternatives.** One route retries each visible error as an independent transient failure. The other inspects host memory and the process tree before admitting replacement work. The retry approach was inadequate because another attempt could add a renderer while the failed attempt’s child still held most of its allocation.

**Decision.** Choose memory observation, child-process cleanup and bounded concurrency. Running free -m exposed the condition that application exceptions did not explain. A render slot is released only when its subprocesses have terminated and their resources are reclaimed; recording a failed job in the control layer is not sufficient evidence.

**Consequences.** Cleanup must cover cancellation, lease loss and encoder failure as well as normal completion. Lower concurrency can increase queue delay, but repeated retries under memory pressure make recovery worse. Keep the original error and resource observations together so operators can distinguish an encoder capability problem from a machine that has run out of memory.
