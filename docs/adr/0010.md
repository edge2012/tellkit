# 0010 — Image references at two launch sites

**Context.** The execution arrangement contains two launch sites that select a container image. Updating only one can leave requests running different dependency sets. This matters for media capability: an FFmpeg build without libx264 previously produced Unknown encoder and left an entire batch without an encoded movie.

**Alternatives.** One route edits the image reference at whichever launch site is immediately visible. The other enumerates both references, changes them as one rollout unit and verifies what each running worker actually uses. The first is quick, but an edited configuration alone does not identify the image of an already running process.

**Decision.** Choose coordinated updates across both launch sites. Compare the selected image identity and check encoder capability in each execution context before considering the rollout complete. A successful job from one context cannot validate the other, because the dependency failure is determined by the image that actually starts the encoder.

**Consequences.** The paired update adds rollout and rollback coordination. Image availability, startup failures and older running jobs can temporarily produce mixed behavior. Operational records therefore need the executing image identity alongside job failures, allowing a codec error to be traced to its runtime rather than misclassified as a storyboard problem.
