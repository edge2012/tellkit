# 0014 — Distinguish craft findings

**Context.** Layout and terminology findings were classified as content rejection, making user questions fail as unacceptable content with no retry available. That behavior attached a terminal consequence to an issue of presentation. It also obscured whether the question itself crossed a content boundary or merely needed a better visual treatment.

**Alternatives.** One route collapses all findings into a single failure class and lets every code veto delivery. The other keeps bottom-line rejection codes separate from craft codes and records the evidence for each. A single class simplifies branching but loses the distinction needed to choose a proportionate response.

**Decision.** Choose veto authority only for bottom-line codes; craft codes are recorded for accounting and improvement. Preserve category information through aggregation and user messaging, so a layout warning cannot acquire rejection authority merely by passing through a generic error handler. This directly corrects the failed route that made presentation issues terminal content judgments.

**Consequences.** Code classification needs ownership and review when new findings are introduced. Recording craft issues does not make them desirable; it makes their consequences explicit. The offline adapter can retain visual diagnostics without claiming to review factual content, while geometry errors and encoded-action verification continue to enforce their own execution contracts.
