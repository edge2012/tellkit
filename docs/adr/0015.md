# 0015 — Readable failure messages

**Context.** Users need an explanation that supports a next action, while diagnosis needs the original failure evidence. Memory exhaustion produced 503, LEASE_LOST and ENCODE_FAILED symptoms after orphaned renderers retained 1.2–1.4 GB each. Displaying one raw code as the complete explanation would confuse the symptom with its cause.

**Alternatives.** One route displays the entire structured failure payload in the user interface. The other shows a concise message and retains structured details in diagnostic artifacts. Raw payloads expose useful implementation evidence, but they make users interpret component names and can encourage an inappropriate retry when the host remains overloaded.

**Decision.** Choose a readable summary linked to retained diagnostics. State which stage failed and whether the job can be retried, using the known failure classification. Preserve the original code and supporting observations for investigation. If the cause is not yet established, describe the failed operation instead of inventing a causal explanation.

**Consequences.** Message mappings need maintenance as error categories evolve. Excessive simplification can erase distinctions between content rejection, craft findings and infrastructure failure. Keep retry policy consistent with those categories, and ensure that the diagnostic record survives delivery of the concise message so a later investigation can recover the evidence behind it.
